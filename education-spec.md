# Math Learning Platform Specification

**Product:** Add2Num Math Learning Platform  
**Document status:** Draft for V1 review  
**Version:** 0.1.0  
**Last updated:** 2026-09-23  
**Primary market:** Vietnam

## 1. Product Vision

Build an accessible Vietnamese math-learning platform that helps students practise skills, understand mistakes, and improve through guided exercises.

The platform must prioritize mathematical correctness, clear Vietnamese explanations, student privacy, teacher visibility, and reliable operation on low-cost mobile devices and unstable networks.

## 2. V1 Goal

V1 delivers one complete learning journey:

1. A student opens a practice session.
2. The platform presents addition or subtraction exercises with non-negative integer operands.
3. The student submits an answer.
4. The platform evaluates the answer safely without using floating-point comparison.
5. The student receives the result and a step-by-step explanation.
6. The attempt is stored and contributes to the student's progress.
7. The student can review recent attempts and weak skills.

V1 must be a working vertical slice, not a complete national education platform.

## 3. Scope

### 3.1 In scope for V1

- Student identity and profile identifier.
- Vietnamese user interface text and explanations.
- Addition and subtraction of non-negative integers represented as decimal strings.
- Practice sessions containing generated exercises.
- Short-answer submission.
- Exact answer evaluation.
- Step-by-step solution generation.
- Attempt history.
- Basic skill progress summary.
- Teacher read-only view of a student's progress, subject to authorization.
- REST API with OpenAPI documentation.
- RFC 7807 Problem Details for errors.
- Automated unit, API, security, and mathematical correctness tests.

### 3.2 Out of scope for V1

- National student identity integration.
- School administration and fee management.
- Live classes or video lessons.
- Gamification, leaderboards, and public rankings.
- AI-generated explanations delivered directly to students.
- Fractions, geometry, equations, and advanced algebra.
- Full offline synchronization.
- Parent accounts.
- Automated high-stakes assessment.
- Cross-province reporting.

## 4. Target Users

| User | V1 capabilities |
|---|---|
| `STUDENT` | Start practice, submit answers, view own results and progress. |
| `TEACHER` | View progress for students assigned to the teacher. |
| `ADMIN` | Reserved for future platform administration; no V1 UI is required. |

The server must enforce access control. The client must not be trusted to restrict access by hiding screens.

## 5. Educational Principles

- Give a useful explanation after an incorrect answer.
- Encourage the student to reason before revealing the complete solution.
- Never mark mathematically equivalent valid answers as incorrect because of formatting alone.
- Use age-appropriate Vietnamese language.
- Avoid public ranking of children.
- Treat progress as a learning signal, not a permanent label.
- Allow teachers to understand the error category, not only the final score.

## 6. Curriculum Model

V1 uses the following initial curriculum node:

```text
Curriculum: GDPT-2018
  Subject: Mathematics
    Grade: 3-5 (exact grade mapping: TBD)
      Topic: Whole-number arithmetic
        Skill: Addition and subtraction of non-negative integers
```

The curriculum model must support future expansion without changing historical attempts. Each exercise and attempt stores the curriculum version and skill identifier used at creation time.

### Initial skill identifiers

- `WHOLE_NUMBER_ADDITION`
- `WHOLE_NUMBER_SUBTRACTION`
- `CARRYING_IN_ADDITION`
- `BORROWING_IN_SUBTRACTION`
- `PLACE_VALUE_ALIGNMENT`

The final grade-to-skill mapping requires review by a Vietnamese mathematics educator before release.

## 7. Domain Model

### 7.1 Student

| Field | Type | Rules |
|---|---|---|
| `id` | UUID or opaque string | Generated by the identity system. |
| `displayName` | string | Must not expose unnecessary personal information. |
| `gradeLevel` | integer | Valid Vietnamese school grade; final range TBD. |
| `createdAt` | date-time | Server-managed. |

### 7.2 Exercise

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Server-generated. |
| `operation` | enum | `ADD` or `SUBTRACT`. |
| `leftOperand` | decimal string | Non-negative integer; no numeric primitive limit. |
| `rightOperand` | decimal string | Non-negative integer; no numeric primitive limit. |
| `expectedAnswer` | server-only decimal string | Never returned before submission. |
| `skillId` | string | Must refer to a known skill. |
| `difficulty` | integer | Range 1-5. |
| `explanation` | server-managed content | Must be mathematically verified. |
| `curriculumVersion` | string | Version of the curriculum mapping. |

For subtraction, V1 generates exercises where `leftOperand >= rightOperand`, so the result remains non-negative.

### 7.3 PracticeSession

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Server-generated. |
| `studentId` | opaque string | Taken from authenticated identity. |
| `skillId` | string | Selected skill. |
| `exerciseCount` | integer | V1 default: 10; maximum: 20. |
| `status` | enum | `IN_PROGRESS`, `COMPLETED`, `EXPIRED`. |
| `startedAt` | date-time | Server-managed. |
| `completedAt` | date-time | Set when completed. |

### 7.4 Attempt

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Server-generated. |
| `sessionId` | UUID | Existing practice session. |
| `exerciseId` | UUID | Existing exercise in the session. |
| `studentId` | opaque string | Taken from authenticated identity. |
| `submittedAnswer` | decimal string | Validated as a non-negative integer string. |
| `isCorrect` | boolean | Computed by the server. |
| `errorCategory` | enum or null | Server-computed when incorrect. |
| `explanation` | string | Safe, age-appropriate explanation. |
| `submittedAt` | date-time | Server-managed. |

Possible V1 error categories:

- `BLANK_ANSWER`
- `INVALID_NUMBER_FORMAT`
- `WRONG_TOTAL`
- `PLACE_VALUE_ERROR`
- `CARRYING_ERROR`
- `BORROWING_ERROR`
- `UNKNOWN`

The first implementation may use `WRONG_TOTAL` and `UNKNOWN` until a reliable error classifier is available.

## 8. Mathematical Requirements

### 8.1 Number representation

- Operands and answers are decimal strings.
- Only non-negative integers are supported in V1.
- Leading zeroes are accepted as input and canonicalized for comparison.
- Empty strings, signs, decimal points, whitespace-only values, and non-digit characters are rejected.
- The implementation must support values larger than Java primitive numeric types.
- The implementation must not use `BigInteger` as the core addition algorithm if the existing `MyBigNumber` contract prohibits it.

### 8.2 Addition

The platform must use the existing Add2Num core library or a compatible math-engine abstraction for addition. It must preserve the library's canonical result behavior and progress semantics where applicable.

### 8.3 Subtraction

Subtraction must be implemented with a verified digit-based algorithm or a reviewed arbitrary-precision implementation. The implementation must not silently overflow.

### 8.4 Answer comparison

The comparison process must:

1. Validate the submitted answer format.
2. Canonicalize leading zeroes.
3. Compare canonical decimal values.
4. Return `isCorrect` and an explanation without exposing internal implementation details.

Every arithmetic operation must have oracle tests using an independent reference implementation or mathematically equivalent test oracle.

## 9. API Contract

Base path: `/api/v1`

All request bodies must use `@Valid`. All protected endpoints require authentication. JSON uses lower camel case.

### 9.1 Start practice session

`POST /api/v1/practice-sessions`

**Role:** `STUDENT`

Request:

```json
{
  "skillId": "WHOLE_NUMBER_ADDITION",
  "exerciseCount": 10,
  "difficulty": 2
}
```

The server obtains `studentId` from the authenticated identity. The request must not contain `studentId`.

Response: `201 Created`

```json
{
  "id": "session-id",
  "skillId": "WHOLE_NUMBER_ADDITION",
  "exerciseCount": 10,
  "status": "IN_PROGRESS",
  "startedAt": "2026-09-23T10:00:00Z",
  "exercises": [
    {
      "id": "exercise-id",
      "operation": "ADD",
      "leftOperand": "1234",
      "rightOperand": "897",
      "skillId": "WHOLE_NUMBER_ADDITION",
      "difficulty": 2
    }
  ]
}
```

`expectedAnswer` and any complete solution must not appear in this response.

### 9.2 Submit an answer

`POST /api/v1/practice-sessions/{sessionId}/attempts`

**Role:** `STUDENT`

Request:

```json
{
  "exerciseId": "exercise-id",
  "submittedAnswer": "2131"
}
```

Response: `200 OK`

```json
{
  "attemptId": "attempt-id",
  "exerciseId": "exercise-id",
  "isCorrect": true,
  "errorCategory": null,
  "explanation": "Cộng từ phải sang trái và xử lý phần nhớ ở từng hàng.",
  "submittedAt": "2026-09-23T10:01:00Z"
}
```

The endpoint must be idempotent for the same authenticated student, session, exercise, and idempotency key. The final idempotency mechanism is TBD.

### 9.3 Get session summary

`GET /api/v1/practice-sessions/{sessionId}`

**Role:** owning `STUDENT` or authorized `TEACHER`

Response: `200 OK`

The response includes session status, score summary, and attempts. It must not expose another student's data.

### 9.4 Get student progress

`GET /api/v1/students/me/progress`

**Role:** `STUDENT`

Optional query parameters:

- `skillId`
- `from`
- `to`

Response: `200 OK`

```json
{
  "studentId": "student-id",
  "skills": [
    {
      "skillId": "WHOLE_NUMBER_ADDITION",
      "attemptCount": 20,
      "correctCount": 16,
      "accuracy": 0.8,
      "recentErrorCategories": ["CARRYING_ERROR"]
    }
  ]
}
```

### 9.5 Get student progress as teacher

`GET /api/v1/students/{studentId}/progress`

**Role:** authorized `TEACHER`

The teacher must be assigned to the student or class. The authorization rule and class model are required before implementation.

## 10. Error Contract

All application errors use RFC 7807 Problem Details with at least:

- `type`
- `title`
- `status`
- `detail`

Expected statuses:

| Status | Use |
|---:|---|
| 400 | Invalid request, malformed number, unsupported skill, invalid session state. |
| 401 | Missing or invalid authentication. |
| 403 | User lacks permission. |
| 404 | Session, exercise, or student is not found or not visible. |
| 409 | Duplicate submission or conflicting session state. |
| 422 | Optional future use for semantically invalid educational content. |
| 500 | Unexpected failure with no internal details exposed. |

Do not return expected answers, database errors, stack traces, credentials, tokens, or unnecessary student information in errors.

## 11. Security and Privacy

- Never accept `studentId`, `createdBy`, or ownership fields from an untrusted client.
- Enforce authorization in the server, not only in the UI.
- Store passwords only through a trusted identity provider or secure password hashing mechanism.
- Never hardcode credentials, JWT secrets, API keys, or database passwords.
- Do not log submitted answers together with identifying student information unless explicitly approved.
- Minimize collection of personal data.
- Use opaque identifiers in public API paths where practical.
- Define retention and deletion policies before production deployment.
- Protect teacher reports from cross-school and cross-class access.
- Add audit logging for teacher access to student progress.

## 12. Non-Functional Requirements

### Accessibility

- Support keyboard navigation.
- Provide labels and readable error messages.
- Do not rely on color alone to communicate correctness.
- Target WCAG 2.2 AA for the web client.
- Use Vietnamese text appropriate to the student's age.

### Performance

- API p95 latency target for normal requests: less than 500 ms under expected V1 load.
- Exercise generation must be bounded and deterministic under a test seed.
- Large-number operations must not block request threads indefinitely.

### Reliability

- Attempts must not be silently lost after a successful response.
- Session and attempt writes must be transactional.
- Backups and recovery objectives must be defined before national deployment.

### Compatibility

- Mobile-first web experience.
- Support current major Android browsers and modern desktop browsers.
- Design API responses for low-bandwidth clients.

## 13. Testing Requirements

### Math engine tests

- Known examples for addition and subtraction.
- Leading-zero input.
- Zero values.
- Different operand lengths.
- Carry and borrowing across every digit.
- Numbers longer than primitive numeric limits.
- Invalid input formats.
- Property-based tests such as commutativity for addition.
- Independent oracle comparison.

### API tests

- Authentication and role authorization.
- Student ownership isolation.
- Teacher assignment authorization.
- Request validation.
- Session lifecycle.
- Duplicate submission behavior.
- Correct and incorrect answers.
- RFC 7807 error responses.
- No answer leakage in session-start responses.

### Educational quality tests

- Explanations match the operation and operands.
- Difficulty metadata is valid.
- Every published exercise has a verified answer.
- Vietnamese text is reviewed by an educator.
- Incorrect answers map to an appropriate error category where supported.

## 14. Observability

The platform should provide:

- Structured application logs with no student PII.
- Request correlation IDs.
- Metrics for session starts, submissions, correctness, errors, latency, and abandoned sessions.
- Alerts for elevated error rates and failed writes.
- Audit records for teacher access to student reports.

## 15. Implementation Plan

### Phase 1: Math vertical slice

- Extract or formalize `math-engine` around `MyBigNumber`.
- Add subtraction with tests.
- Define exercise and answer domain objects.
- Implement deterministic exercise generation.
- Implement answer evaluation.
- Add unit tests and oracle tests.

### Phase 2: Student practice API

- Add student authentication integration.
- Implement practice-session creation.
- Implement answer submission.
- Persist attempts.
- Add Problem Details and security tests.

### Phase 3: Progress

- Implement session summaries.
- Implement student progress aggregation.
- Add error-category reporting.
- Add simple recommendation rules.

### Phase 4: Teacher workflow

- Add class and teacher assignment model.
- Add teacher progress views.
- Add audit logging and access review.

### Phase 5: Pilot readiness

- Mobile-first client.
- Accessibility review.

- Pilot with a small number of schools before wider deployment.

## 17. V1 Definition of Done

- The selected grade and skill mapping is approved by an educator.
- The math engine passes unit, property-based, and oracle tests.
- Students can start a session and submit answers.
- Correct and incorrect answers are evaluated accurately.
- Explanations are reviewed and shown in Vietnamese.
- Attempts and progress are persisted transactionally.
- Student data is isolated by authorization tests.
- No expected answer is leaked before submission.
- API contract is documented in OpenAPI.
- RFC 7807 errors are used consistently.
- No secrets or sensitive personal data are committed or logged.
- A pilot deployment can be built, tested, monitored, backed up, and recovered using documented procedures.
