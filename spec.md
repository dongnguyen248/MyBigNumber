# Work Order API Specification

**Status:** Draft for review  
**Version:** 0.1.0  
**Last updated:** 2026-09-23  
**Source:** `docs/br-analysis-wo.md`, `docs/api-rules.md`, `docs/security-rules.md`, `docs/coding-rules.md`

## 1. Purpose

Add a Spring Boot API module to the Add2Num project for managing work orders created by field technicians and viewed or managed by supervisors.

The API must use the existing Add2Num core library as a dependency boundary. It must not copy or reimplement the `MyBigNumber` addition algorithm.

## 2. Scope

### In scope

- Create a work order for an active equipment item.
- List work orders with filtering and pagination.
- Retrieve one work order by ID.
- Update a work order status according to the state transition rules.
- List active equipment items for client-side selection and validation.
- Authenticate API clients and enforce technician/supervisor authorization.
- Return validation and application errors using RFC 7807 Problem Details.

### Out of scope for this version

- User registration and user administration.
- Equipment creation, update, or deletion.
- Work-order deletion unless explicitly approved.
- Push notifications.
- Offline synchronization.
- Complex organizational or site-level permissions.
- A new implementation of big-number addition.

## 3. Actors and Authorization

| Actor | Permissions |
|---|---|
| `TECHNICIAN` | Create work orders; list and view work orders; list active equipment. |
| `SUPERVISOR` | List and view work orders; update work-order status; list active equipment. |

Every protected endpoint requires an authenticated user. The client must not provide `createdBy`; the API obtains it from the authenticated security context.

### Authentication decision

**TBD:** Confirm the identity provider and token/session mechanism with the security owner.

The implementation must not assume that "all logged-in users are technicians" means authentication can be skipped. At minimum, server-side authentication and role checks are required.

## 4. Domain Model

### 4.1 WorkOrder

| Field | Type | Required | Rules |
|---|---|---:|---|
| `id` | `Long` or `UUID` | response only | Generated by the server and immutable. Final choice: **TBD**. |
| `equipmentId` | string | yes | Must identify an existing equipment item with status `ACTIVE`. |
| `description` | string | yes | Must not be blank. Maximum length: **TBD**. |
| `priority` | enum | yes | One of `LOW`, `MEDIUM`, `HIGH`, `URGENT`. |
| `status` | enum | response only | One of `NEW`, `IN_PROGRESS`, `DONE`. New work orders start as `NEW`. |
| `createdBy` | string | response only | Obtained from the authenticated user. Client input is forbidden. |
| `createdAt` | date-time | response only | Set by the server. |
| `updatedAt` | date-time | response only | Set by the server and updated on status changes. |

### 4.2 Equipment

| Field | Type | Required | Rules |
|---|---|---:|---|
| `equipmentId` | string | yes | Unique equipment identifier. |
| `name` | string | yes | Display name. |
| `status` | enum | yes | `ACTIVE` or `INACTIVE`. |

Only equipment with status `ACTIVE` may be associated with a newly created work order.

### 4.3 User

| Field | Type | Rules |
|---|---|---|
| `id` | `Long` | Server-generated identifier. |
| `username` | string | Unique login identity. |
| `role` | enum | `TECHNICIAN` or `SUPERVISOR`. |

Password storage and user-management APIs are outside this specification. The API must not log credentials, tokens, or other sensitive authentication data.

## 5. State Transitions

The initial state is `NEW`.

| Current status | Allowed next status | Authorized role |
|---|---|---|
| `NEW` | `IN_PROGRESS` | `SUPERVISOR` |
| `IN_PROGRESS` | `DONE` | `SUPERVISOR` |
| `NEW` | `DONE` | **TBD** |
| `DONE` | none | none |

Invalid transitions must return an appropriate 400 response using Problem Details. The final transition policy requires Product Owner confirmation before implementation.

## 6. API Contract

Base path: `/api`

All JSON field names use lower camel case. The API must not expose fields that are not defined in the endpoint schemas below.

### 6.1 Create work order

`POST /api/work-orders`

**Authorization:** authenticated `TECHNICIAN`

Request body:

```json
{
  "equipmentId": "EQ-001",
  "description": "Inspect hydraulic pump",
  "priority": "HIGH"
}
```

Request rules:

- `equipmentId` is required and must not be blank.
- `description` is required and must not be blank.
- `priority` is required and must be one of the declared enum values.
- Unknown or client-controlled fields such as `id`, `status`, `createdBy`, `createdAt`, and `updatedAt` must not be accepted as business input.
- The equipment must exist and be `ACTIVE`.

Success:

- Status: `201 Created`
- Body: `WorkOrderResponse`
- The response must include the generated ID and server-managed fields.

Failure cases:

- `400 Bad Request`: malformed or invalid request, invalid priority, or inactive/nonexistent equipment.
- `401 Unauthorized`: no valid authentication.
- `403 Forbidden`: authenticated user is not a technician.
- `500 Internal Server Error`: unexpected server failure without exposing internals.

### 6.2 List work orders

`GET /api/work-orders`

**Authorization:** authenticated `TECHNICIAN` or `SUPERVISOR`

Supported query parameters:

- `priority`: optional `LOW`, `MEDIUM`, `HIGH`, or `URGENT`.
- `status`: optional `NEW`, `IN_PROGRESS`, or `DONE`.
- `page`: optional zero-based page number. Default: **TBD**.
- `size`: optional page size. Maximum: **TBD**.

Success:

- Status: `200 OK`
- Body: typed paginated response, not a raw top-level array.

The visibility scope is unresolved: all work orders versus site/area/supervisor scope. **TBD: Product Owner.**

### 6.3 Get work order

`GET /api/work-orders/{id}`

**Authorization:** authenticated `TECHNICIAN` or `SUPERVISOR`

Path parameter:

- `id`: valid work-order identifier.

Success:

- Status: `200 OK`
- Body: `WorkOrderResponse`

Failure cases:

- `400 Bad Request`: malformed identifier.
- `401 Unauthorized`: no valid authentication.
- `403 Forbidden`: authenticated user lacks permission.
- `404 Not Found`: work order does not exist or is outside the caller's visibility scope.

### 6.4 Update work-order status

`PATCH /api/work-orders/{id}/status`

**Authorization:** authenticated `SUPERVISOR`

Request body:

```json
{
  "status": "IN_PROGRESS"
}
```

Rules:

- The body must contain exactly the supported status field.
- Only valid state transitions are accepted.
- `createdBy`, timestamps, and other work-order fields cannot be changed by this endpoint.

Success:

- Status: `200 OK`
- Body: updated `WorkOrderResponse`

Failure cases:

- `400 Bad Request`: invalid status or invalid transition.
- `401 Unauthorized`: no valid authentication.
- `403 Forbidden`: caller is not a supervisor.
- `404 Not Found`: work order does not exist.

### 6.5 List active equipment

`GET /api/equipments/active`

**Authorization:** authenticated `TECHNICIAN` or `SUPERVISOR`

Success:

- Status: `200 OK`
- Body: typed response envelope containing active equipment items.
- The response must not be a raw top-level array.

## 7. Response Schemas

### WorkOrderResponse

```json
{
  "id": 1001,
  "equipmentId": "EQ-001",
  "description": "Inspect hydraulic pump",
  "priority": "HIGH",
  "status": "NEW",
  "createdBy": "technician01",
  "createdAt": "2026-09-23T10:15:30Z",
  "updatedAt": "2026-09-23T10:15:30Z"
}
```

The final identifier type and timestamp serialization must be fixed in the OpenAPI contract before implementation.

### PaginatedWorkOrderResponse

The exact envelope is **TBD**, but it must be a typed object rather than a raw list. It should define the item collection and pagination metadata consistently for all collection endpoints.

### Problem Details

All errors use RFC 7807 fields:

```json
{
  "type": "https://example.invalid/problems/validation-failed",
  "title": "Validation Failed",
  "status": 400,
  "detail": "Field 'description' must not be blank."
}
```

Required fields:

- `type`: URI identifying the problem type.
- `title`: short human-readable summary.
- `status`: HTTP status code.
- `detail`: safe human-readable detail.

Do not expose stack traces, SQL, database messages, tokens, secrets, or internal implementation details.

## 8. Persistence Requirements

The persistence implementation should use Spring Data JPA/Hibernate or parameterized queries. User input must never be concatenated into SQL or JPQL.

Expected tables/entities:

- `work_orders`
- `equipments`
- `users`, or an integration mapping to the external identity system

Expected work-order indexes:

- `equipment_id`
- `priority`
- `status`
- `created_at`

The database engine, migration tool, foreign-key strategy, retention period, and seed data are **TBD**.

## 9. Non-Functional Requirements

- Java 17 or later.
- Spring Boot 3.3 or later.
- Constructor injection only.
- Public methods must not return `null`; use `Optional` or a specific exception where applicable.
- Use enums for fixed value sets.
- Keep methods focused and generally below 30-40 lines.
- Use SLF4J parameterized logging.
- Do not log passwords, tokens, PII, or sensitive equipment ownership data.
- Do not hardcode secrets in source code, configuration, tests, or documentation.
- API responses must not expose database internals.
- The API must be testable without requiring production credentials.

## 10. Acceptance Criteria

### Create

- A valid authenticated technician can create a work order for active equipment.
- The API returns `201 Created` and the complete `WorkOrderResponse`.
- The server assigns status `NEW`.
- The server obtains `createdBy` from authentication, not from the request body.
- A missing or blank required field returns `400` Problem Details.
- An unknown or inactive equipment ID cannot create a work order.
- A supervisor or unauthenticated caller cannot use the technician-only operation.

### Read

- An authenticated permitted user can list work orders.
- Filtering by priority and status works as specified.
- Pagination metadata is present and consistent.
- An authenticated permitted user can retrieve an existing work order.
- A missing work order returns `404` Problem Details.

### Status update

- Only a supervisor can update status.
- Valid transitions succeed.
- Invalid transitions fail with `400` Problem Details.
- A completed work order cannot be changed.

### Security and quality

- No hardcoded secrets exist.
- No string-concatenated SQL or JPQL exists.
- All request bodies use `@Valid`.
- Protected endpoints have server-side authorization.
- Unexpected errors do not disclose stack traces or database details.
- Unit, controller, persistence/integration, and security tests cover positive and negative paths.

## 11. Open Decisions Before Implementation

1. Separate Spring Boot application or Maven multi-module reactor structure?
2. Final authentication mechanism and identity-provider integration?
3. Final work-order ID type: `Long` or `UUID`?
4. Maximum description length and equipment-ID format?
5. Default page size and maximum page size?
6. Work-order visibility scope for technicians and supervisors?
7. Whether `NEW -> DONE` is allowed?
8. Database engine and migration tool?
9. Equipment and user data ownership: local database or external service?
10. Retention, deletion, notification, and offline-sync requirements?

No implementation prompt should silently resolve these questions. Each decision must be recorded in this specification or in an ADR before the affected code is generated.

## 12. Definition of Done for the API Module

- The architecture decision is recorded.
- All open decisions affecting the first release are resolved.
- `openapi.yaml` matches this specification.
- The Spring Boot module compiles with Java 17+.
- Unit, controller, persistence/integration, and security tests pass.
- The core `add2num` library is consumed through its declared API/dependency boundary.
- No undocumented endpoint, request field, response field, or business rule is introduced.
- Security review finds no unresolved critical or high-severity issue.
- A fresh checkout can build and test the API using documented commands.
